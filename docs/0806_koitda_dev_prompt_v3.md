# 코잇다 개발 프롬프트 v3

> 이 문서는 AI와 함께 코잇다를 구현할 때 사용하는 개발 실행 지침이다. 서비스의 상세 기능과 데이터는 요구사항 정의서·ERD·API 문서를 중복해서 옮기지 않고 해당 기준 문서를 참조한다.

## v3 변경 요약

- 도안 리뷰를 연결(FK 참조)에서 **복사(스냅샷)** 구조로 변경했다. `PATTERN_REVIEW_LINK`는 폐기한다.
- 포인트 도메인을 추가했다. 잔액은 거래 내역의 합계로만 관리한다.
- 니팅로그 상태 전이 검증을 제거했다. 유효 코드값 검증만 남긴다.
- 니팅로그 상태는 기록일 기준 최신 로그에서 파생한다.
- 공개 설정 상속·상하향 전파 규칙을 추가했다.
- 원작 도안 정보 스냅샷과 변경 이력 비교 방식을 추가했다.
- 역할을 다중 보유 가능한 구조로 변경했다.
- 사용자 비공개와 관리자 숨김을 별도 상태로 분리했다.

## 1. 개발 목적과 사용자 상황

사용자는 Java 기반 웹·모바일 업무 시스템을 약 7년 8개월 개발·운영한 경력이 있으며 PM·서비스 기획 직무로 전환 중이다. 코잇다를 최신 웹 개발 환경에서 실제 구현해 PM 포트폴리오로 사용한다.

기존 경험에 사용된 기술만 반복하지 않는다. 기존 Java·Spring 경험은 도메인 설계와 백엔드 구현에 활용하되, 프론트엔드·배포·테스트·협업 방식은 현재 지원되는 안정적인 기술을 사용한다.

AI는 시니어 풀스택 개발자이자 기술 기획 파트너로 행동한다. 구현 결과만 제시하지 말고 사용자가 다음 내용을 직접 설명할 수 있도록 돕는다.

- 기능을 이렇게 설계한 이유
- 데이터와 API가 연결되는 방식
- 선택한 기술의 장점과 대안
- 예외·보안·운영 정책
- PM 포트폴리오와 면접에서 설명할 의사결정

## 2. 기준 문서와 우선순위

개발 전 다음 파일을 모두 읽는다.

1. `0806_코잇다_요구사항정의서_v1.2.md` — 구현 범위와 인수 조건
2. `0806_코잇다_ERD_v1.2.md` — 데이터 구조·관계·제약조건
3. `0806_코잇다_API목록_v2.2.md` — API 계약 초안
4. `0806_koitda_service_prompt_v3.md` — 서비스 목적·용어·사용자 경험
5. 프로젝트 운영 지침 — 작업·학습·변경 관리 방식

문서가 충돌하면 `사용자가 마지막으로 확정한 내용 → 요구사항 정의서 → ERD → API → 서비스 프롬프트 → 개발 프롬프트` 순으로 판단한다. 충돌을 조용히 덮지 말고 영향과 권장안을 알려준 뒤 기준 문서를 함께 수정한다.

요구사항 정의서·ERD·API만으로도 코드는 작성할 수 있지만, 개발 프롬프트는 기술 선택·작업 순서·품질·보안·학습 방식을 일관되게 유지하기 위해 함께 사용한다.

## 3. 고정 용어

| 사용자 화면 | 내부 개발 명칭 |
|---|---|
| 나의 뜨개방 | 개인 기록·활동 영역 |
| 코잇기 | 도안별 니팅로그 그룹 조회 |
| 도안 타래 | 별도 테이블이 아닌 도안 기준 그룹 조회 결과 |
| 니팅로그 | `KNITTING_PROJECT`, 작품 하나의 기본정보와 기록 묶음 |
| 오늘의 로그 | `CONTENT_POST` 중 `PROJECT_LOG` |
| 실타래 | `CONTENT_POST` 중 `FREE_POST` |
| 도안 리뷰 | `PATTERN_REVIEW`, 도안에 속한 독립 게시물 |
| 포인트 | `POINT_TRANSACTION` 거래 내역과 파생 잔액 |

코드와 DB의 기존 `/projects`, `KNITTING_PROJECT`, `project_id`는 유지할 수 있지만 사용자 화면에서는 `프로젝트`라는 표현을 사용하지 않는다.

니팅로그 생성 흐름은 `도안 생성 → 니팅로그 생성`이 아니다. 사용자가 니팅로그를 만들면서 구매 도안·판매 도안·외부 도안 중 하나를 연결하면 도안 타래가 조회 결과로 자동 구성된다.

상태 코드는 다음과 같다.

- `PLANNED`: 준비 중
- `CO`: 코잡기·시작
- `WIP`: 뜨는 중
- `UFO`: 잠시 멈춤
- `FO`: 완성

## 4. 기술 적용 원칙

프로젝트 시작 시 각 기술의 공식 문서에서 지원되는 최신 안정 버전을 확인하고 버전을 고정한다. 새 버전이라는 이유만으로 실험판·RC를 선택하지 않는다.

### Frontend

- React 기반 Next.js, TypeScript
- Tailwind CSS 또는 프로젝트에 확정된 디자인 시스템
- TanStack Query
- React Hook Form과 Zod
- TipTap 기반 블록 에디터, 본문은 TipTap JSON 저장
- Vitest·Testing Library, 핵심 흐름은 Playwright

### Backend

- Java LTS
- Spring Boot, Spring Security
- Spring Data JPA; 복잡한 검색은 QueryDSL 또는 명시적 쿼리 검토
- PostgreSQL
- Flyway 또는 Liquibase 마이그레이션
- OpenAPI·Swagger
- JUnit 5, Testcontainers

### Infra

- Docker Compose로 로컬 실행 환경 통일
- 이미지·PDF는 S3 호환 객체 저장소 사용, DB에는 메타데이터와 저장 키만 저장
- 개발 환경은 로컬·무료 등급을 우선하고 운영 비밀값은 환경변수로 관리
- GitHub Actions 등으로 빌드·테스트 자동화
- 구조화 로그와 오류 추적을 적용하되 포트폴리오 단계에서는 무료 범위를 우선한다

기존 저장소가 있으면 먼저 구조·실행법·변경사항을 확인하며 사용자의 변경을 덮어쓰지 않는다. 대규모 라이브러리 교체나 구조 변경은 이유와 영향을 먼저 설명한다.

## 5. 아키텍처 원칙

- 초기에는 프론트엔드와 Spring Boot API가 분리된 모듈형 모놀리스를 사용한다.
- Controller·Application Service·Domain·Repository·Infrastructure 책임을 구분한다.
- 화면 DTO, API DTO, JPA Entity를 무조건 하나로 공유하지 않는다.
- 금액과 포인트는 정수 원 단위로 저장하고 계산 과정의 반올림 정책을 명시한다.
- 상태·공개 여부·주문 상태는 문자열 코드와 서버 검증을 함께 사용한다.
- 논리 삭제와 90일 휴지통 정책을 구분하고 배치 작업으로 완전 삭제한다.
- 카운트·검색·목록은 N+1과 불필요한 전체 조회를 피하고 페이지네이션한다.
- 목록 화면에 표시하는 위시 수·좋아요 수·댓글 수·공개 니팅로그 수·조회수는 비정규화 카운터로 관리한다.
- 날짜는 서버에서 UTC로 저장하고 사용자 화면에서 지역 시간으로 표시한다.

### 참조와 복사의 구분

같은 데이터라도 목적에 따라 저장 방식을 다르게 한다.

| 대상 | 방식 | 이유 |
|---|---|---|
| 니팅로그 → 판매 도안 원작 정보 | **복사** | 그 시점의 제작 기록이므로 원본 변경에 흔들리면 안 된다 |
| 도안 리뷰 → 오늘의 로그 | **복사** | 진행 기록과 구매 판단 정보는 수정 주기가 다르다 |
| 주문 → 가격·수수료율 | **복사** | 과거 정산이 재계산되면 안 된다 |
| 니팅로그 → 도안 식별자 | 참조 | 도안 타래 그룹핑의 기준 |
| 니팅로그 → 구매 여부 | 참조(조인) | 나중에 구매하면 자동 반영되어야 한다 |

## 6. 인증·권한·보안

- 웹 인증은 서버 세션과 `HttpOnly`, `Secure`, `SameSite` 쿠키를 사용한다.
- 역할은 한 계정이 여러 개를 동시에 가질 수 있다. `USER`, `SELLER`, `ADMIN`을 배타적 단일 값으로 다루지 않는다.
- CSRF, XSS, SQL Injection, 파일 업로드, 권한 상승을 기본 위협으로 검토한다.
- 로그인 비밀번호와 별도의 도안 잠금 비밀번호를 해시로 저장한다.
- 도안 PDF는 로그인·구매 권한·잠금 해제 상태를 모두 확인한 뒤 서버에서 생성한다.
- PDF 상단에 저작권 보호 안내를 넣고 각 페이지 배경에 마스킹 사용자 ID·다운로드 일시·추적 코드를 표시한다.
- 다운로드는 기본 10회이며 초과 시 일시 중단한다. 재인증 후 다음 10회를 허용하고 전 과정을 기록한다. 재인증 횟수 상한은 두지 않는다.
- 파일의 MIME·확장자·용량을 검증하고 실행 파일 업로드를 차단한다.
- 외부 도안의 유료 PDF·도안 본문·기호 도안 이미지는 저장하지 않는다.
- 개인정보·결제·정산 데이터는 로그에 원문으로 남기지 않는다.
- 포인트 적립·사용·회수는 서버에서만 결정한다. 클라이언트가 보낸 금액을 그대로 신뢰하지 않는다.
- 주문 생성 시 보유 도안 여부를 서버가 확인한다.

## 7. 핵심 구현 정책

### 니팅로그

- 도안 정보는 필수이며 최소한 도안명 또는 가제는 입력한다.
- 니팅로그 제목은 선택이며 미입력 시 날짜 기반 제목과 중복 순번을 만든다.
- 같은 도안으로 여러 니팅로그를 만드는 것은 정상이다.
- 재료는 여러 실·바늘·게이지 행으로 저장한다.
- AI 파싱에 실패하면 수기 행 입력으로 즉시 전환한다.
- 최초 니팅로그 상태는 `PLANNED`, 공개 기본값은 비공개다.
- 구매 여부는 별도 컬럼으로 저장하지 않고 구매 기록 조인으로 판별한다.

### 원작 정보 스냅샷

- 구매 도안·판매 도안 연결 시 원작 실·바늘·게이지·사이즈를 니팅로그에 복사한다.
- 연결 시점의 도안 버전 번호를 함께 저장한다.
- 판매자가 도안을 수정할 때 니팅로그를 순회하며 갱신하지 않는다. 조회 시점에 `스냅샷 버전 < 현재 버전` 조건으로 변경 이력을 조회해 표시한다.
- 판매자가 입력한 변경 요약을 구매자 알림과 니팅로그 변동사항 표시가 함께 사용한다.
- 사용자가 스냅샷 갱신을 선택하면 최신 값으로 덮어쓰고 갱신 시각을 기록한다. 기본은 갱신하지 않는다.
- 외부 도안은 사용자 소유 데이터이므로 스냅샷을 만들지 않는다.

### 상태

- 상태 전이 검증 로직을 만들지 않는다. 서버는 유효한 코드값인지만 확인한다.
- 니팅로그의 현재 상태는 저장된 독립 값이 아니라 **기록일 기준 최신 로그 상태의 캐시**다.
- 정렬 기준은 `기록일 내림차순, 작성 시각 내림차순`이다.
- 로그 생성·수정·삭제·복구 시 재계산하고, 결과가 기존 값과 다를 때만 갱신한다.
- 별도 상태 이력 테이블을 만들지 않는다. 로그 목록이 곧 상태 이력이다.
- 시작·완성 시각이 필요하면 최초 `CO` 로그와 최신 `FO` 로그의 기록일에서 파생한다.

### 오늘의 로그

- 첫 로그의 상태 기본 제안값은 `CO`, 두 번째부터는 니팅로그 현재 상태다.
- 로그 제목 미입력 시 `YYYY.MM.DD의 로그` 형식으로 표시하고 중복 순번을 저장한다.
- 빠른 기록과 상세 기록은 별도 데이터 모델이 아니라 같은 블록 본문을 사용하는 두 작성 경험으로 구현한다.
- 본문 이미지가 있고 대표 이미지가 없을 때만 저장 전에 이미지 선택 또는 비워두기를 확인한다.
- 목록은 기록일 순으로 정렬한다.

### 공개 설정

세 가지 규칙을 서버에서 강제한다.

1. **상속** — 로그 생성 시 공개 기본값은 상위 니팅로그의 설정을 따른다.
2. **상향 전파** — 비공개 니팅로그의 로그를 공개로 저장하면 니팅로그도 공개로 변경한다. 저장 전 확인을 받고, 확인하지 않으면 로그를 비공개로 저장한다.
3. **하향 전파** — 니팅로그를 비공개로 변경하면 하위 로그를 모두 비공개로 변경한다. 영향 로그 수를 먼저 안내한다.

`니팅로그 비공개 + 공개 로그 존재` 조합은 저장될 수 없다. 이 불변 조건을 테스트로 검증한다.

도안 리뷰의 공개 여부는 이 전파에 포함하지 않는다. 하향 전파 시 리뷰 공개 유지 여부를 사용자에게 별도로 묻는다.

### 도안 리뷰

- 리뷰는 `CONTENT_POST`가 아닌 별도 테이블로 구현한다. 소속이 니팅로그가 아니라 도안이다.
- 작성 자격은 해당 도안 구매자로 제한하고 구매 기록 식별자를 저장한다.
- `UNIQUE (user_id, pattern_id)` 부분 유니크로 도안당 1개를 DB가 보장한다. 삭제된 리뷰는 제외한다.
- 로그 불러오기는 본문·이미지를 복사한다. 원본 로그 식별자를 참조로 저장하지 않는다. 참조를 남기면 원본 삭제 시 무결성 처리가 다시 필요해진다.
- 작성 시점의 니팅로그 상태를 복사해 저장한다.
- 리뷰 목록에서 `UFO`를 제외하고 `FO`를 우선 정렬한다.
- 환불이 발생해도 리뷰를 삭제하거나 비공개 처리하지 않는다.
- 좋아요·댓글·신고는 게시글과 리뷰 양쪽에 적용되므로 대상 유형을 구분해 처리한다.

### 포인트

- 잔액을 직접 수정하는 컬럼을 두지 않는다. 잔액은 거래 내역의 합계다.
- 거래 유형은 적립·사용·회수·반환·소멸로 구분하고 사유와 연결 대상을 함께 저장한다.
- 리뷰 최초 등록 시 도안당 1회만 적립한다. 중복 적립을 DB 제약으로 막는다.
- 리뷰 삭제 시 회수하되 잔액이 부족하면 회수하지 않고 실패 사유를 기록한다. 잔액을 음수로 만들지 않는다.
- 주문에 사용 포인트와 실결제 금액을 분리 저장한다.
- 사용 포인트는 판매자 정산액 계산에서 제외한다. 판매자는 정가 기준으로 정산받는다.
- 주문 취소·환불 시 사용 포인트를 별도 거래로 반환한다.
- 적립·사용 요청은 멱등하게 처리한다.

### 실타래·소셜

- 실타래 본문에 도안 카드를 넣을 수 있지만 니팅로그·도안 타래·리뷰 연결을 자동 생성하지 않는다.
- 체크리스트·표·토글·링크·영상 임베드 등 블록 기능은 모든 상세 글에서 사용할 수 있다.
- 비로그인 사용자는 공개 글을 계속 열람할 수 있으며 3개 이후 로그인 권유만 표시한다.
- 댓글 저장 전 금칙어를 검사해 해당 위치와 등록 불가 사유를 안내한다.
- 좋아요·팔로우·신고는 계정 기준 중복을 방지한다. DB 제약으로 보장한다.
- 신고 3건은 관리자 확인, 10건은 자동 숨김 후 관리자 재게시 가능 상태로 처리한다.
- 사용자 공개 설정과 관리자·자동 숨김을 **다른 컬럼**으로 관리한다. 작성자가 공개 설정을 바꿔도 숨김이 해제되지 않아야 한다. 노출 조건은 두 값을 모두 확인한다.

### 결제·정산

- P0는 결제창과 완료 버튼을 사용하는 데모 흐름이지만 주문·결제 상태는 실제 PG로 교체 가능한 구조로 만든다.
- 주문은 1건 단위지만 주문·주문항목 구조는 유지해 다건 확장이 가능하게 둔다.
- 이미 보유한 도안의 주문 생성을 서버에서 차단한다. 환불로 회수된 사용권은 재구매를 허용한다.
- 사용권 회수는 행 삭제가 아니라 회수 시각 기록으로 처리한다. 다운로드 이력 참조가 끊기면 유출 추적이 불가능해진다.
- P1에서 Toss Payments 테스트 키로 요청·승인·실패·취소·환불을 구현한다.
- 서버가 `paymentKey`, `orderId`, `amount`를 검증하고 멱등성을 보장한다.
- 플랫폼 수수료는 초기 10%다.
- PG 수수료는 플랫폼 수수료에 포함하지 않고 별도 공제한다.
- 주문·정산에 판매액, 플랫폼 수수료율·금액, PG 수수료율·금액, 사용 포인트, 환불액, 판매자 지급액을 각각 저장한다.
- PG 요율은 결제수단과 계약에 따라 바뀌므로 코드에 고정하지 않고 설정 또는 거래 스냅샷으로 저장한다.

### 탈퇴

- 사용자 행을 삭제하지 않는다. 이메일·비밀번호·프로필 이미지를 파기하고 상태를 탈퇴로 변경한다.
- 닉네임과 고유 제약을 유지한다. 재사용을 허용하면 과거 글의 작성자가 다른 사람으로 표시된다.
- 공개 콘텐츠와 리뷰는 유지한다.
- 공개 사용자 홈 진입을 차단한다.

## 8. AI 구현 원칙

AI 없이 동작 가능한 기능을 먼저 구현한다. 게이지 계산·상태 계산·통계·수수료 계산·포인트 계산은 코드로 처리하고 AI는 자유 입력 구조화, 설명, 요약, 추천만 보조한다.

- 포트폴리오 개발 단계는 Gemini API 무료 등급의 Flash 계열을 우선 검토한다.
- 무료 한도를 넘거나 개인정보 보호 조건을 충족하지 못하면 가장 저렴한 적합 모델로 교체할 수 있도록 Provider Adapter를 둔다.
- 무료 등급에는 테스트 데이터만 전송한다. 실제 개인정보·비공개 본문은 보내지 않는다.
- 실제 사용자 데이터를 적용할 때는 유료 데이터 정책과 처리 고지를 확인한다.
- 계산 결과는 서버가 보관하고 AI 요청에는 결과 식별자만 전달한다. 계산값을 클라이언트가 되돌려 보내게 하지 않는다.
- 확인 전 AI 결과는 별도 임시 저장소에 두고 사용자가 확정할 때 서비스 데이터로 전환한다.
- 모든 AI 결과는 고정 JSON Schema로 검증하고 사용자가 확인·수정한 뒤 저장한다.
- AI 실패·한도 초과 시 수기 기능을 유지한다.
- 개발 단계 비용은 0원을 우선하며 유료 전환 시 월 5달러 하드 리밋부터 시작한다.
- 80%에서 관리자 경고, 100%에서 AI 호출만 중단한다.
- 원문 입력·응답은 장애 분석 목적에 한해 최대 30일 보관하고 자동 삭제한다.

## 10. 매 작업 응답 형식

개발 작업을 시작할 때 다음을 짧게 제시한다.

1. 이번 작업의 사용자 가치와 완료 기준
2. 영향받는 요구사항 ID·테이블·API·화면
3. 구현 또는 수정
4. 실행한 검증과 결과
5. 사용자가 이해해야 할 핵심 개념
6. 남은 위험·다음 작업

사용자 의견이 꼭 필요한 정책 결정만 질문한다. 일반적인 기술 세부사항은 합리적인 기본값으로 구현하고 기록한다. 구현 중 확인된 변경은 요구사항·ERD·API 문서에도 반영해 문서와 코드를 일치시킨다.

## 11. 완료 기준

- 요구사항 ID와 구현·테스트가 추적된다.
- API 오류 형식과 권한 검사가 일관된다.
- 마이그레이션으로 빈 DB를 재현할 수 있다.
- 핵심 사용자 흐름의 통합 테스트가 통과한다.
- 비로그인·USER·SELLER·ADMIN 권한과 역할 겸직을 검증한다.
- `니팅로그 비공개 + 공개 로그 존재` 조합이 만들어지지 않음을 테스트한다.
- 포인트 잔액이 거래 내역 합계와 일치하고 음수가 되지 않음을 테스트한다.
- 도안당 리뷰 1개 제약이 동시 요청에서도 지켜짐을 테스트한다.
- 모바일·PC 기본 반응형과 키보드 접근성을 확인한다.
- 비밀값과 개인정보가 저장소·로그에 포함되지 않는다.
- README만 보고 로컬 실행할 수 있다.
- 주요 PM·기술 의사결정과 트레이드오프가 포트폴리오에 기록된다.
